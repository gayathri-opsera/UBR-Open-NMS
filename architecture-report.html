Section 2 — What Works Well

Before diving into risks — genuine strengths observed in the codebase that deserve recognition.

✅ Global JWT Auth Enforcement at Gateway

The API gateway enforces JWT RS256 authentication and hierarchical RBAC (admin › operator › user) as global Express middleware — applied before any route handler. This ensures no route can accidentally bypass auth. Public paths are explicitly allowlisted rather than relying on opt-in auth. Source: services/api-gateway/src/middleware/jwt.middleware.js + rbac.middleware.js.

✅ Per-Service GitHub Actions CI/CD Pipelines

Each of the 15+ microservices has a dedicated GitHub Actions workflow. The hotspot analysis shows 204 commits in 6 months with consistent CI activity. This means each service change is independently tested and built — no monolithic build bottleneck. Source: .github/workflows/ (15 per-service YAML files).

✅ Redis Sliding-Window Rate Limiter with User-Scoped Keys

The rate limiter uses a proper sliding-window algorithm (ZREMRANGEBYSCORE + ZADD + ZCARD) scoped per req.user.sub. This is more accurate than fixed-window counters and prevents "reset burst" attacks. It also returns X-RateLimit-Limit and X-RateLimit-Remaining headers. Source: services/api-gateway/src/middleware/ratelimit.middleware.js.

✅ Circuit Breaker + Correlation IDs on All Proxy Routes

Every downstream proxy call is wrapped in an opossum circuit breaker. All requests receive a x-correlation-id header for distributed tracing, and the correlation ID is propagated to all downstream headers. Source: services/api-gateway/src/proxy/proxy.js + middleware/correlation.middleware.js.

✅ Immutable Audit Trail with 1-Year Retention

A dedicated audit-service is part of the architecture with documented 1-year retention for immutable audit logs. This satisfies compliance requirements for operator actions (config changes, alarm acknowledgements). Source: README.md — audit-service description + services/audit-service/.

✅ Well-Structured Shared Libraries Across 4 Languages

The shared-libs/ directory contains typed interfaces for TypeScript, Java POJOs, Go structs, and Python dataclasses — enabling contract alignment across the polyglot stack. Test fixtures (3 samples per model) are also shared. This reduces schema drift risk in event-driven communication.

S — Spoofing (2 threats)
HIGH x-user-role Header Spoofing via Internal Network

Asset: All downstream microservices (notification, alarm, inventory, audit)

Proxy injects x-user-id and x-user-role from validated JWT. Downstream services trust these headers without re-verifying the JWT. If Istio is in PERMISSIVE mode (no PeerAuthentication found), any internal pod can forge these headers and gain admin access.

Countermeasures: Existing: Istio mTLS (PERMISSIVE, not enforced) | Recommended: Add PeerAuthentication STRICT + each downstream service should validate a service-account JWT
MEDIUM Unauthenticated SSE Stream Subscription

Asset: /api/v1/notifications/stream — real-time alarm and device events

SSE stream is in PUBLIC_PATHS — any unauthenticated client can subscribe. Network fault data, alarm severity, and provisioning events are exposed without credentials.

Countermeasures: Existing: None | Recommended: Remove from PUBLIC_PATHS; use JWT query param for EventSource
T — Tampering (1 threat)
LOW Synthetic Device Metrics Presented as Real Data

Asset: Topology UI — device CPU, memory, latency, link quality

topology.stub.js generates all metrics via deterministic math on d.id.length. NOC operators make decisions on fabricated data. Data integrity is broken at the presentation layer.

Countermeasures: Existing: None | Recommended: Connect to real monitoring endpoints (Prometheus/SNMP)
I — Information Disclosure (2 threats)
MEDIUM Real-time Operational Data via Unauthenticated SSE

Real-time alarm severity, device status, and provisioning events are accessible to unauthenticated external clients. For a telecom NMS, this reveals network fault patterns.

MEDIUM Unencrypted Inter-Service Traffic (PERMISSIVE mTLS)

No Istio PeerAuthentication found. Istio defaults to PERMISSIVE mode — plaintext HTTP fallback is allowed. Device configuration, alarm data, and KPI streams may traverse unencrypted.

D — Denial of Service (2 threats)
CRITICAL Rate Limiter Fail-Open on Redis Failure

Redis downtime disables all per-user rate limiting. Attackers can brute-force auth endpoints or flood APIs without throttling during Redis unavailability.

HIGH 80% Circuit Breaker Threshold — Late Protection

CB opens only after 80% of requests fail. At 500 req/min, ~400 users experience failures before protection kicks in.

E — Elevation of Privilege (1 threat)
HIGH x-user-role Admin Escalation from Internal Network

Without STRICT mTLS, any pod can send x-user-role: admin to inventory or alarm service and gain full admin CRUD access — bypassing the RBAC layer entirely.

Section 4 — Deep Insights

4a. Configuration Contradictions

⚠️ Timeout Chain Inversion: CB 30s > K8s Liveness Probe 5s

Config A CB_TIMEOUT_MS: 30,000ms — api-gateway/src/config/index.js
Config B liveness.timeoutSeconds: 5s — helm-charts/api-gateway/values.yaml

When a downstream service hangs, the circuit breaker holds the gateway connection open for 30 seconds. But K8s liveness probe times out at 5 seconds and restarts the gateway pod — healthy gateway pods are killed before the CB can open. Result: false-positive cascading pod restarts under downstream load.

Fix: liveness.timeoutSeconds: 35 (CB timeout + buffer) or reduce CB_TIMEOUT_MS to <5s.
⚠️ CORS Origin Port Mismatch: localhost:3001 vs containerPort 3010

Config A cors.origin: "http://localhost:3001" — api-gateway/src/config/index.js (default)
Config B containerPort: 3010 — helm-charts/api-gateway/values.yaml

The gateway runs on port 3010 in K8s but the default CORS origin allowlist targets port 3001. Without CORS_ORIGIN env override in K8s, all browser requests from the frontend will be rejected by CORS policy.

Fix: Set CORS_ORIGIN=https://nms.airtel.internal in K8s ConfigMap / Helm values.
